# Acopio — Handoff Notes

Read this first when picking the project back up in a new editor/session. It's the "how does this actually fit together, and what's the state of things right now" doc — for the spec/rules/design system themselves, see the pointers in [Other docs in this repo](#other-docs-in-this-repo) below; this file doesn't repeat them.

## What this is

A Chrome extension (Manifest V3). Hover any element on any website → a floating tooltip identifies what it is (color / font / image / component) and lets you "+ Collect" it into a local, per-site library. Local-only, no backend, no network calls except to the page you're already on. Built for a designer doing competitive UI research — the differentiator is *selective* hover-capture, not a full-page scraper.

Sibling project: `../acopio-figma-plugin` — a real Figma plugin that imports Acopio's JSON export and rebuilds captured components as actual Figma layers. Currently gated off in the deployed build (see [Feature flags](#feature-flags)) but the code and export format are being kept in sync — see that project's own `CONTEXT_HANDOFF.md`.

## Architecture / file map

```
manifest.json                  MV3 manifest — permissions, content_scripts list, side_panel
src/
  background.js                 Service worker: message router + screenshot capture queue
  db/db.js                      IndexedDB wrapper — AcopioDB global
  content/
    shared.js                   Acopio.ICONS (all SVG icon defs), shared constants — loads FIRST
    sanitize.js                 Acopio.sanitizeCaptureElement — strips scripts/handlers/PII before anything else touches captured HTML
    tagger.js                   Acopio.detectTag — classifies a hovered element as color/font/image/component
    overlay.js                  The hover tooltip itself — by far the largest file (~2500 lines): rendering, capture, copy-to-clipboard, note field, collection stack
    toolbar.js                  The persistent floating pill (bottom-right) — separate UI from the tooltip, toggles hover-capture on/off, opens the side panel
    notes.js                    Second, independent capture mode — text-selection-triggered, own toggle, own shadow-DOM tooltip. See "Notes capture" below.
    content.js                  DOM extraction: extractComponentLayers (the actual layer/CSS extraction for a component capture), Acopio.buildCaptureData/finalizeCapture/etc — the public API the other content scripts call into
  sidepanel/
    sidepanel.html/.css/.js     The side panel — Library (by-site and by-Collection views), Compare/Pairing view, Export, multi-select
vendor/jszip.min.js             Only third-party dependency — ZIP export
test/                           Static HTML fixtures (design-preview-*.html render tooltip/sidepanel in isolation; xss-adversarial.html is the Section 9 sanitization test page)
```

Content scripts load in this exact order (manifest.json) because each depends on the previous one's globals being attached to `window.Acopio` first: `shared.js → sanitize.js → tagger.js → overlay.js → toolbar.js → notes.js → content.js`. All content scripts run in the page's **isolated world** — `window.Acopio` from a content script is invisible to the page's own JS and to anything you `javascript_exec` against the page from outside (see [Isolated world gotcha](#isolated-world--youll-hit-this-again) below).

## Data model

IndexedDB, database name `acopio-db`, schema version `1` (db.js). Three object stores:

- **`items`** (keyPath `id`) — every captured thing. Indexed on `hostname`, `type`, `family`, `capturedAt`. Shape (varies by `type`): `{ id, type: "color"|"font"|"image"|"component", hostname, selector, family, note, capturedAt, data: {...type-specific} }`. Component `data` includes `outerHTML` (sanitized), `previewImage` (captured screenshot dataURL), `boundingBoxWidth/Height`.
- **`collections`** (keyPath `id`) — user-curated groupings, distinct from the automatic per-hostname folders. `itemRefs: [{ folderHostname, itemId }]` — **never a copy of the item**, always resolved live against `items` on render (`AcopioDB.resolveCollectionItems`). This is a hard invariant from GROUND_RULES.md — don't cache/duplicate item data into a collection.
- **`meta`** (keyPath `key`) — misc key/value state.

Any schema change → bump `CURRENT_SCHEMA_VERSION` in db.js and write a real migration in the `onupgradeneeded` handler. Don't silently break existing users' stored items.

## Message-passing (background.js)

Content scripts can't touch `chrome.tabs.captureVisibleTab` or IndexedDB-adjacent APIs directly in all cases, and the side panel needs to reach the service worker too. Everything goes through `chrome.runtime.onMessage`:

| `message.type` | Purpose |
|---|---|
| `CONTENT_SCRIPT_READY` | Content script announces it's alive on this tab |
| `OPEN_SIDE_PANEL` | Content script (toolbar button) asks background to open the side panel — `sidePanel.open()` is only callable from a background/extension-page context |
| `CAPTURE_VISIBLE_TAB` | Screenshot request — see [Screenshot capture queue](#screenshot-capture-queue-backgroundjs) below |
| `CHECK_DUPLICATE` | "Have I already collected something like this on this site?" — proactive duplicate flag before saving |
| `GET_RECENT_ITEMS` | Powers the tooltip's collection-stack preview on a return visit |
| `UPDATE_NOTE` | Edit an item's note after capture (sidepanel's pencil/edit affordance) |
| `UPDATE_ITEM_DIMENSIONS` | Best-effort correction once a captured image's real naturalWidth/Height is known |

### Screenshot capture queue (background.js)

`chrome.tabs.captureVisibleTab` is rate-limited by Chrome (~2/sec) and every hovered element fires a **passive preview capture** (`captureElementScreenshot(el, "preview")` in overlay.js). A single global FIFO queue (`queueCaptureVisibleTab`) spaces dispatches ≥550ms apart and retries on the rate-limit error specifically. On top of that, passive preview requests are **cancellable** — each carries a `previewToken`, and a request whose token is no longer the tab's latest (i.e. you've since hovered something else) is skipped entirely rather than wasting a dispatch slot on a result nobody wants. An explicit **Copy click always dispatches for real** (`purpose` omitted, not `"preview"`) — the user is actively waiting on that one, it's never cancelled.

This queue is the thing to look at first if screenshots start silently failing/timing out again — see [Known issue: copy-image timeout under load](#known-issue-fresh-capture-can-time-out-under-heavy-queue-load) below.

## The tooltip (overlay.js) — capture → copy flow

1. Hovering settles on an element → `Acopio.detectTag` (tagger.js) classifies it → `content.js`'s `extractComponentLayers`/`buildTypeData` pulls the actual data (colors, font metrics, image URL, or component layer tree + sanitized HTML) → tooltip renders.
2. A **passive preview screenshot** fires in parallel (`captureElementPreview` → `captureElementScreenshot(el, "preview")`) — small (480px-wide cap × devicePixelRatio), lossy JPEG, meant only for the in-tooltip thumbnail and the collection-stack thumbnails. Cached as `lastElementCapture` / on the item as `data.previewImage`.
3. Clicking **Copy** (`copyForPaste` → `resolveCopyImageBlob`) always fires its **own fresh, full-resolution capture first** (`captureElementScreenshot(el)`, no `"preview"` purpose → uncapped resolution, lossless PNG) — only falls back to the smaller cached preview if that fresh capture genuinely fails. The clipboard write is **image-only when an image was captured** — no competing `text/plain`/`text/html` — because a paste target that's offered both will pick text over image, and there's no Clipboard API lever to express a preference; not offering the competing format is the only way to force an image-aware target to use the image. Text formats are the fallback only when there's truly no image.
4. Clicking **+ Collect** → `Acopio.finalizeCapture` → saved to IndexedDB, `sessionCaptures` (in-memory, this page load) gets it, the tooltip swaps into the collection-stack view.

## Notes capture (notes.js) — a second, independent capture mode

Highlighting text on a page (instead of hovering an element) shows a small separate tooltip offering to collect that text as a `type:"note"` item — plus any images/links the selection happens to cross. Off by default; its own toggle (floating toolbar pill + side panel topbar, both mirroring the existing hover-capture toggle's exact wiring pattern) writes `acopioNotesActive` to `chrome.storage.local`, completely independent of `acopioActive`.

**Deliberately architecturally isolated from overlay.js** — own shadow-DOM host (`data-acopio-notes-root`, distinct from the tooltip's `data-acopio-root`), own state, own Escape/outside-click/dismiss listeners, own copy of the design-token CSS values (same duplication-not-import pattern `toolbar.js` already uses). Nothing in overlay.js's render/generation/concurrency machinery is touched — notes.js could be deleted outright and the hover tooltip would be completely unaffected. This was a hard constraint from the user when the feature was requested.

**Trigger**: a real, non-collapsed `window.getSelection()` — no second gesture for images/links. A drag-selection's `Range` can already span across `<img>`/`<a>` elements, so `extractMediaFromRange` just inspects what the resulting range actually contains (`range.intersectsNode(el)`) rather than inventing a separate "select an image" interaction browsers don't naturally support. Fires from both `mouseup` (fast path) and a debounced `selectionchange` listener (covers keyboard selection — Shift+Arrow, Ctrl+A). Both funnel into the same `handleSelectionSettled()`, which is deliberately idempotent (`rangesEqual` check) and won't clobber an in-progress interaction (typing a note, using the folder picker) just because the redundant debounced fire lands ~350ms after mouseup already opened it.

**Save flow**: reuses the *existing* `CAPTURE_ITEM` background handler unmodified (it was already generic enough — its one type-specific branch only fires for `component`). Two new, small, additive background message handlers support the rest: `GET_COLLECTIONS` (populates the tooltip's "Save to" folder picker — content scripts can't reach `AcopioDB` directly) and `ADD_ITEMS_TO_COLLECTION` (thin relay onto the existing `AcopioDB.addItemsToCollection`, so a note can be filed straight into a chosen Collection at capture time — itemRefs-only, per GROUND_RULES.md, never a data copy).

**No DB schema/version change was needed** — confirmed via the `items` store's already-generic `type` index (the pre-existing, if incomplete, `"pairing"` type was the precedent) — `type:"note"` is just another value, not a schema change. `findSimilarItem` (db.js) got a `note` dedup branch (exact-text match within hostname) so it doesn't silently skip dedup like an unhandled 5th type otherwise would.

**Library rendering**: notes render via their own `buildNoteTile` (sidepanel.js), not the existing `buildTile`/`buildRichCard` — those assume an image-hero shape that doesn't fit plain text. Notes also get their own single-column section layout (`.grid-section-items-notes`) instead of the fixed 3-column grid every other type uses, since a text excerpt needs real width to stay legible. Per-note download-as-`.txt`/copy actions plus a "Download all" (one combined `.txt`, not a ZIP — the natural shape for a stack of text) on the section header.

## Export to Figma / Notion (Google-gated cloud export)

Third and fourth export destinations alongside the existing "Export as ZIP" — added per direct request: "add option while exporting to as zip or to figma or to notion and while exporting you will need login to there figma or notion via google." Lives in the same export dropdown as ZIP (`.export-menu`, both the Sites-tab and multi-select bars).

**A pre-existing piece of infrastructure this builds on, worth knowing about if you haven't seen it before**: this project already has a real, configured Supabase project (`src/config.local.js`, gitignored, present since the very first commit — not something added for this feature) wired up in `src/db/supabase-client.js`, previously used for nothing but a `ping()`/session-check stub (`GET_SUPABASE_STATUS`). HANDOFF.md's own "no backend" framing above is about the *capture/storage* path (IndexedDB stays the only source of truth for captured items) — it was never quite true of the project's full dependency surface once Supabase entered the picture. This feature is the first thing to actually build on that Supabase project.

**Three separate account connections, because they're three genuinely different things:**

1. **"Sign in with Google" — a Acopio-level identity gate**, via Supabase Auth's Google provider (`src/db/supabase-client.js`'s new `signInWithGoogle()`). This is what the "login via google gmail" part of the request literally maps to. It does **not** by itself grant access to Figma or Notion's APIs — it only establishes who's using Acopio. Implemented with the standard Chrome-extension pattern for Supabase Auth (no custom redirect page exists, or is needed): `supabase.auth.signInWithOAuth({ provider: "google", options: { skipBrowserRedirect: true } })` builds the authorize URL without navigating anywhere, `chrome.identity.launchWebAuthFlow` opens it in its own auth window, and the `access_token`/`refresh_token` Supabase appends to the redirect URL's fragment are handed to `supabase.auth.setSession()` — that call is what actually persists the session (through the `chromeStorageAdapter` already in `supabase-client.js`), not the redirect itself.
2. **"Connect to Figma"** (`src/db/cloud-oauth.js`'s `connectFigma()`) — Figma's own OAuth app, exchanged with PKCE. Figma's app type is a genuine public client, so this entire exchange (including the `code_verifier`) happens safely client-side, in the extension — no secret involved at all.
3. **"Connect to Notion"** (`connectNotion()`, same file) — Notion's own OAuth integration. Notion's token exchange is Basic-Auth'd with `client_id:client_secret` (a confidential-client flow) — a secret shipped inside an extension bundle is extractable by anyone who unpacks it, so this one step is proxied through a new Supabase Edge Function, `supabase/functions/notion-oauth-exchange/index.ts`. The extension only ever sends that function the one-time authorization code; the function holds the real secret (via `supabase secrets set NOTION_CLIENT_SECRET=...`) and does the exchange server-side. This is genuinely the smallest "backend" this project could get away with for this feature — not a general-purpose server, one function, one job.

**⚠️ A hard technical wall that shaped this, worth understanding before extending it**: Figma's public REST API has **no endpoint that creates design nodes** (frames, rectangles, text layers) in a file — that capability only exists inside the Figma app itself, via the Plugin API. This is exactly *why* this project already has a separate companion Figma plugin (`../acopio-figma-plugin`, see the top of this doc) that imports a JSON export and rebuilds items as real layers — there's no way around that plugin for actually creating Figma content, OAuth or not. So: the Figma OAuth connection above is real and works (verifies the account) but **doesn't itself create anything in Figma** — pushing real content is entirely `../acopio-figma-plugin`'s job, via the actual Plugin API, and always was. **`ENABLE_FIGMA_EXPORT` is now `true`** (flipped on this session, per direct instruction — "Figma's own Plugin API use it" — after confirming the plugin already fully supports the current v2 export format). Originally there were three separate Figma menu items; per a same-session follow-up ("i want export to figma not Export for Figma Plugin") they were merged to two: **"Export to Figma"** now directly downloads the full v2 JSON payload (all item types, not just colors) that the plugin's `code.js` already parses (`buildComponentCardFromTree` etc. — layoutTree-aware) — this *is* `performPluginJsonExport()` now, just under the name people actually expect. **"Copy for Figma plugin"** stays as the clipboard-instead-of-file alternative for the plugin's own "Paste from clipboard" button. The old standalone "Export for Figma Plugin" button was removed (redundant once "Export to Figma" did the same thing), and so was the earlier colors-only `navigator.clipboard` SVG-copy version of "Export to Figma" that existed before that merge — one button, one real meaning, not three overlapping ones. The new Figma OAuth connection (`cloud-oauth.js`) isn't wired into any of these three buttons — it exists for a future "pick a target file" picker if this ever needs one, not because today's plugin-based flow needs it. Don't let anyone (including a future you) assume "Connect to Figma" (OAuth) is what makes layers appear — it isn't; the plugin is.

**"Export to Notion" is the one that's fully real end to end** — Notion's REST API genuinely supports creating pages and blocks. `performNotionExport()` (sidepanel.js): checks Google sign-in → checks Notion connection (prompting either if missing) → `NOTION_SEARCH_PAGES` lists pages the user has shared with the integration → a picker modal (reuses the same `.sp-modal-picker` shell/row shape as the Collection picker — see item 31 below) → `notionBlocksForItems()` converts the export scope's items into real Notion blocks (a heading + content per item: images become a real Notion "external" image block since captured image URLs are already reachable https URLs; components stay text-only with a note pointing at the ZIP export, since their preview is a `data:` URL screenshot and Notion's image block needs an externally reachable URL, not inline bytes — a stated limitation, not a silent gap) → `NOTION_CREATE_PAGE` creates the page (chunked into 100-block appends past Notion's per-call cap) → opens the new page in a tab on success.

**Setup required before any of this actually works** (none of it can be done for you — each needs an account you control):
1. `figma.com/developers/apps` → create an app → its client ID goes in `src/config.local.js` as `ACOPIO_FIGMA_CLIENT_ID`. No secret needed.
2. `notion.so/my-integrations` → create a public integration → client ID goes in `config.local.js` as `ACOPIO_NOTION_CLIENT_ID`; the client **secret** goes to `supabase secrets set NOTION_CLIENT_SECRET=...` (server-side only, never in the extension).
3. Both apps need the same redirect URI registered: `chrome.identity.getRedirectURL()`'s output for this specific unpacked extension (a `https://<extension-id>.chromiumapp.org/` URL — the ID is stable for an unpacked extension as long as its path doesn't move).
4. Supabase project (`Authentication → Providers`) needs Google OAuth enabled as a sign-in provider.
5. `supabase functions deploy notion-oauth-exchange` to actually stand up the proxy.
6. A Notion workspace member has to explicitly share at least one page with the integration (Notion's own permission model — the integration can't see anything not explicitly shared) before the page picker will show anything.

Until all six are done, every button here fails informatively (`"Figma isn't configured yet — add ACOPIO_FIGMA_CLIENT_ID..."` etc.) rather than silently — see the error-message strings in `cloud-oauth.js` and `supabase-client.js` directly if one shows up unexpectedly.

## What changed this session (most recent work, in order)

Useful context for *why* things look the way they do — the reasoning, not just the diff.

1. **Tooltip permanently stuck invisible after an extension reload.** Root cause: `captureElementScreenshot`'s hide/restore-own-UI-while-capturing logic used a **per-call** snapshot of `Acopio.ownRoots`' visibility. Hovering across several elements fires several *overlapping* capture calls (each settled hover fires its own), and the second call's "snapshot of the original visibility" could actually be the first call's already-hidden state — whichever call finished last then "restored" to that corrupted snapshot, leaving the UI hidden forever. Fixed with a shared reference-counted pair (`rootsHideCount` / `rootsTrueVisibility` in overlay.js) — only the first concurrent hide records the true original value, only the last matching restore (count back to 0) applies it.
2. **Copy pasted as plain text description instead of the image**, even though a real, correctly-sized PNG was genuinely present in the clipboard write (verified directly via `navigator.clipboard.read()`) — the paste *target* was choosing `text/plain` over `image/png` when both were offered, which the Clipboard API's writer side has no way to override. Fixed by writing image-only when an image exists (see flow above).
3. **Copied image was correctly-shaped but low-resolution/lossy** (an 862×551 component came through as 257KB). Two stacked causes in `captureElementScreenshot`: an output-width cap (`480 * devicePixelRatio`) and a lossy JPEG encode, both originally meant only for the small passive preview thumbnail but shared with the Copy code path. Fixed: `purpose === "preview"` keeps the small/lossy behavior; anything else (Copy) gets uncapped resolution + a lossless PNG encode straight off canvas. Also reordered `resolveCopyImageBlob` to attempt a **fresh** full-res capture first rather than preferring the cached (small, lossy) preview capture — otherwise the resolution fix wouldn't actually take effect in the common case, since a preview capture had usually already succeeded before the Copy click.
4. **Collection-stack overflow badge (`+N`) was hardcoded at 4 cards**, showing "+2" etc. even when there was visibly more room. Replaced with `MAX_STACK_SLOTS`, computed once from the real fixed CSS numbers (`.card` is a constant 280px, not responsive) — cards now fill until they'd encroach on the 12px gap reserved before the collect button, then overflow. See the constant block right above `let sessionCaptures = []` in overlay.js for the actual math if this needs revisiting.
5. **List-view density toggle removed** from the side panel topbar (user's explicit call after being shown the icon — see the button's old `#density-toggle` id if you're grepping history). The Library now always renders in compact/grid mode. The now-dead `list`/`grid` icons were removed from `Acopio.ICONS` (shared.js) since nothing else referenced them — check before reusing those names for something new.
6. **Item action icons (delete/download/edit) made consistent between the compact tile and the expanded "rich card"** (the bigger preview used in Family/type-grouped views, e.g. "COMPONENTS — 8"). Previously: download only existed for images, edit only existed on the compact tile (and used a different corner-inset convention than download — literally hung outside the tile's edge while download tucked inside it). Now: `buildDownloadBtn`/`buildEditBtn` are shared helpers used by both `buildTile` and `buildRichCard`; download also appears for components (`downloadOneComponent`, sourced from `data.previewImage` since components don't have a live source URL the way images do); edit's CSS now tucks inside the corner the same way download does, and `.tile-note-badge` (which occupies the same slot once a note exists) was aligned to the identical inset so the corner doesn't visibly jump when a note gets added.
7. **Figma export gated off for deployment, not deleted.** `const ENABLE_FIGMA_EXPORT = false;` at the top of sidepanel.js. With it off, the chevron dropdown next to "Export as ZIP" (which only ever held the three Figma-related menu items) hides itself, and the primary ZIP button gets its full pill shape back (`.export-split-solo` CSS) instead of looking cut off. Flip the flag to `true` locally to keep developing that feature — nothing else needs to change.
8. **Note field in the tooltip converted from `<input>` to `<textarea>`** with JS auto-resize (`autosizeNoteField`, reads `scrollHeight`) — grows as you type, caps at 3 lines (`max-height: calc(1.4em * 3 + ...)`, tied to the field's own font-size rather than a guessed pixel number), then scrolls vertically past that instead of continuing to stretch the tooltip. **First version of this had a real bug**, caught by live testing right after: the initial `autosizeNoteField()` call ran immediately after `cardEl.appendChild(noteField)`, but `cardEl` itself isn't attached to the shadow tree until `shadow.appendChild(cardEl)` — 20-odd lines later in `render()`. Reading `scrollHeight` on a still-detached node measures ~0, and that got locked in as the field's inline height, so every fresh empty note field rendered as an ~18px sliver instead of its real ~35px. Fixed by moving the initial autosize call to right after `shadow.appendChild(cardEl)`, where the field actually has a layout box. If `autosizeNoteField`-style patterns get reused elsewhere in this codebase, the rule is: **never read `scrollHeight`/layout off a node before its ancestor chain reaches the actual document (or shadow root) — a detached subtree always measures as empty**, regardless of what's been appended to it internally.
9. **Escape used to only fire while the hover tooltip happened to be open** (`if (!isVisible()) return;` gated the whole listener) — reworked so Escape always pauses hover-capture (`acopioActive: false`), whether or not a tooltip is currently showing, giving a standalone keyboard shortcut instead of requiring a click on the toolbar's toggle icon. Tradeoff worth knowing: this now catches *every* Escape press on the page, including ones meant for the host site's own UI (closing its own modal, clearing its own search box) — non-destructive, one click undoes it, but a real behavior change, not just a narrower bugfix.
10. **Notes capture (notes.js) — a whole second, independent capture mode** added: highlight text on a page (not hovering) to collect it as a `type:"note"` item, with its own on/off toggle (floating toolbar + side panel), optional filing into a Collection at capture time, and a dedicated "Notes" section in the Library. Full detail in [Notes capture](#notes-capture-notesjs--a-second-independent-capture-mode) above — architecturally isolated from the hover tooltip on purpose (own shadow-DOM host, own state, own listeners), so it doesn't touch `overlay.js`'s existing behavior at all.

Needed one CSS addition: `.card-download-btn`'s hover-reveal rule only targeted `.tile:hover`/`.card:hover`, not `.folder-card:hover`, so the button would have been permanently invisible without `.folder-card:hover .card-download-btn { opacity:1; ... }` added.

15. **Clipboard copy architecture rebuilt end to end** (`sidepanel.js`). The real, root-caused bug: `navigator.clipboard.write()` reliably supports exactly **one** `ClipboardItem` per call, not an array of several — an earlier version building one `ClipboardItem` per selected item and handing an array to `.write()` failed identically regardless of item count. Rewritten around the actual correct pattern (same technique Docs/Notion/Figma-style rich copy uses): **one** `ClipboardItem` carrying **two MIME representations** — `text/plain` (items joined with `---` dividers) and `text/html` (same descriptions, HTML-escaped, with up to a **global budget of 6 total images** across the whole copy inlined as base64 `data:` URIs). The image budget is computed synchronously in one pass *before* any async fetching starts (checking a shared counter from inside already-started parallel per-item work would race — every item's callback runs synchronously up to its first `await`, so all would read the same pre-decrement value). Both payload values are Promises so `.write()` still fires synchronously within the click's user-activation window. 17. **Two real security bugs found via deliberate adversarial testing, both fixed:**
    - `isJavascriptUri` (`sanitize.js`, shared by `notes.js`) only matched `/^\s*javascript:/i` — tolerant of *leading* whitespace only. Browsers strip embedded ASCII tab/newline/CR from **anywhere** in a URL during parsing and still execute it as the intended scheme — a real, documented XSS filter-evasion technique (`java\tscript:alert(1)` and friends), not theoretical. Both `sanitize.js`'s check and `notes.js`'s own separate `data:` URI check had this gap; fixed by stripping those three characters from the whole string before testing. Verified live against the exact bypass strings plus a battery of legitimate URLs (zero false positives).
    - The 4,000-char note-text truncation cap (`notes.js`) used plain `text.slice()`, which cuts by UTF-16 code unit, not code point — a cut landing inside a surrogate pair (most emoji) left a dangling unpaired surrogate, invalid when later UTF-8-encoded (the `.md` export, clipboard text). Fixed with a `safeTruncate()` that backs off one unit when the cut would split a pair.
    - Separately: the truncation itself (`extraction.truncated`) was computed but **never surfaced anywhere** — no UI warning, not saved on the item. A selection over ~4,000 characters (trivially easy) got silently cut with zero indication. Fixed: a visible warning banner in the tooltip (stacks with the existing PII banner rather than overlapping it), `data.truncated` persisted on the saved item, and shown in the `.md` export / copy description text.

2. After any source edit: reload the extension in `chrome://extensions`. **This does not update already-open tabs** — a tab that was open before the reload keeps running the old content script until you refresh *that tab* too. (Confirmed directly this session: a stale tab reproduced an already-fixed bug after an extension reload, until refreshed.)
3. No build step — everything is loaded as plain `<script>`-equivalent MV3 content scripts, no bundler, no TypeScript. Editing a `.js` file and reloading is the entire dev loop.
4. Syntax-checking without reloading the extension: any static file server + `fetch(url).then(r=>r.text()).then(src => new Function(src))` in any browser console will throw on a real syntax error without needing to touch the extension at all. Useful for a fast sanity check before spending a reload cycle.

## Gotchas you'll hit again

- **Isolated world**: content scripts' `window.Acopio` is invisible both to the page's own JS *and* to `javascript_exec`-style automation run against the page (different JS world). `document.querySelector('[data-acopio-root]')` (the tooltip's shadow-DOM host, tagged with that attribute in overlay.js) is the one thing that's reliably visible cross-world, since DOM nodes are shared even when script-scoped globals aren't.
- **`chrome://` pages are unreachable by browser automation** — can't load, inspect, or reload the extension from tooling. A human has to do that step.
- **Two separate shadow-DOM hosts exist**: the tooltip's own host (overlay.js, `data-acopio-root` attribute) and the floating toolbar's host (toolbar.js, `ensureHost()`, **no** `data-acopio-root` attribute). Don't assume one implies the other is present/working.
- **MV3 `clipboard.write()` rejects `image/jpeg`** as a `ClipboardItem` key even when the blob's own type matches — everything that goes into a clipboard write gets re-encoded to PNG first (`urlToPngBlob`), with a fast-path that returns an already-PNG blob unmodified (no re-encoding, no quality loss) rather than round-tripping through canvas again.
- **A single `ClipboardItem` can carry multiple format representations, but the paste target chooses which one to use** — the writer (this extension) has no API-level way to express "prefer this format." The only real lever is not offering a competing format at all (see the Copy flow above).
- **The side panel document itself cannot be reached by any browser automation available in this project — confirmed repeatedly, a hard platform limitation, not a tooling gap to work around.** This is separate from (and in addition to) the `chrome://` restriction above — the side panel's own URL isn't a `chrome://` page, it's a genuine extension page, and it's still unreachable. Practical consequence: anything side-panel-specific (Library grid, Collections, Compare view, Export UI, the multiselect/download/alignment work in items 12–14 above) can only be verified by a human's own eyes in real Chrome — don't claim to have "tested" a side-panel change without one. Content-script surfaces (the hover tooltip, notes tooltip, floating toolbar) on regular `http`/`https` pages ARE reachable and were how most of the live verification in items 15–28 above was actually done.
- **Automation coordinate scaling is real and will burn you — verify with `elementFromPoint`, don't trust visual pixel-matching against a screenshot.** Discovered directly this session: a browser-automation `hover` call requesting screen coordinate (142, 322) produced a real `mousemove` event whose `e.clientX/clientY` the page actually received as (115, 261) — a consistent ~1.234× scale mismatch on that particular tab (likely device-pixel-ratio/zoom-related, tab-specific, not universal). This produced a very convincing-looking "wrong element got targeted" false bug report before the mismatch was found. **The fix/check**: before trusting any hover-based live test result, independently confirm the real element under the cursor via `document.elementFromPoint(x, y)` in the SAME coordinate space you requested — if it doesn't match what you expected, suspect the tooling's coordinate mapping before suspecting the extension.
